VERDICT: PROCEED WITH CHANGES

### 1. A half-written session becomes permanent
- Severity: major
- Claim: Nothing makes a session's 12 rows atomic, yet step 5 never recomputes a session already in the log.
- Why it matters: A shutdown or crash mid-session leaves, say, 5 of 12 rows; the session counts as logged and the hole is frozen into the record.
- Fix: Write the 12 rows in one DuckDB transaction, and have the status file flag any session without exactly 12 rows.

### 2. First contact with real vendor data is unattended
- Severity: major
- Claim: All tests are synthetic, and neither the bar check nor the paper trader has ever seen a real Twelve Data response.
- Why it matters: A mismatch (bar count, timestamp convention, timezone) either rejects every session or passes and writes wrong fills into a log that is never recomputed.
- Fix: Before enabling the task, run fetch-and-check only on one real session before 2026-11-17 and confirm bar count and first/last timestamps.

### 3. No rule for a session that never passes the check
- Severity: major
- Claim: Step 6 retries forever and only flags; it does not say whether later sessions proceed.
- Why it matters: One permanently bad day either stalls the log behind it, or leaves a hole inside the 14-session warm-up. Deciding which after seeing results breaks the registered rule.
- Fix: Register the rule now: after N failures, write an explicit no-data row for all 12 candidates and continue.

### 4. The status file cannot show a run that never happened
- Severity: major
- Claim: `forward_status.md` is only regenerated by a run that reaches step 7.
- Why it matters: If the task is disabled, starts in the wrong working directory, or the trader throws, the file still shows the last good state with 0 missing.
- Fix: Regenerate the status in a `finally` block, use absolute paths, and put the generation time and last session covered on the first line.

### 5. Missed-start runs fire before the network is up
- Severity: minor
- Claim: A missed-start run triggers at boot or login, often before the network is connected.
- Why it matters: If the PC is usually off at 18:00, every run is a boot-time run; each download fails, and the next attempt is the next boot.
- Fix: Set the task to start only when a network is available and to restart on failure every 10 minutes, a few times.
